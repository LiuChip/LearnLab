# LearnLab 设计评估与开工报告

> 日期：2026-09-02
>
> 本报告基于当前总设计、架构、安全、数据模型、路线图、UI 和插件加载设计，作为开工前的二次评估。

## 结论摘要

当前设计已经从“大而全的平台设想”收敛为一个可以开工的小型本地软件：

- 核心是实验包播放器，不负责云服务、课程质量判断或环境内核；
- 实验包是内容和声明，插件是环境、判定器、面板和工具能力；
- 插件按全局插件、当前实验包直接依赖和递归依赖链加载；
- 插件以 `AppContext`、`PackageContext` 接收上下文，学习区组织关系由核心掌握；
- 权限顶层分为读、写、执行，具体再按资源、动作和作用域细分；
- 学习区用一个 `workspace.db` 管理包、软连接和共享依赖，实验包用一个 `package.db` 管理进度和摘要；
- 实验细节保留为文件，设置和插件设置使用可导入/导出的 JSON；
- GitHub/自定义源只保证下载和导入完整性，不建立复杂市场审核体系。
- 桌面 UI 直接对标 VSCode Workbench；当前原型的视觉完成度不足，属于需要尽快修正的产品风险，而不是继续保留的最终布局。

**综合评价：可以开始实现，但必须先做纯逻辑解析器和只读播放器，不要一开始同时做市场、第三方插件生态、LabKit 或云能力。**

## 已解决的严重问题

| 问题 | 当前决策 | 评价 |
|:---|:---|:---|
| 插件越权访问学习区 | 默认仅通过 API 访问 LearnLab 本体和当前实验包；其他包、`workspace.db`、任意用户文件不在默认作用域 | P0 风险得到边界化；仍需诚实说明不是 OS 沙箱 |
| 插件 API 尚不清晰 | 采用 `AppContext` + `PackageContext`；权限分读/写/执行，细分为资源和动作 | 入口简单、可渐进扩展，避免一次性设计庞大 API |
| 插件加载范围混乱 | `GlobalPlugins ∪ Closure(package.required_plugins)`，全局插件对所有包可用，包级插件按依赖链加载 | 能支持 Vim 模拟等全局增强，也避免加载所有已安装插件 |
| 插件身份和市场过度复杂 | 最小身份为 ID、版本、作者、签名；源由 GitHub 或用户自定义 | 与小项目规模匹配；签名不能被宣传为安全认证 |
| 云同步和备份范围过大 | 核心不做云；导出设置 JSON，用户自行复制学习区；同步由插件完成 | 大幅降低核心复杂度，责任边界清楚 |
| 依赖重复安装 | 依赖仓库提供常见独立运行时，小众运行时可随包携带；最终在学习区 `dependencies/` 按版本/平台/架构/哈希复用 | 兼顾包体积、离线导入和同学习区多包共享 |
| 进度迁移过度设计 | 包移动到未登记位置默认丢失绑定；复制整个学习区通常保留；必要时使用软连接 | 符合小项目和正常用户场景，但 UI 必须提示后果 |

## 架构评价

### 做得好的部分

1. **核心边界明确**：SQLite 只服务 LearnLab 自身元数据，MySQL/Python/C++ 等环境不混入核心。
2. **插件加载和插件权限被分开**：一个插件可以全局激活，但仍需按当前包创建上下文，不自动获得全局文件权限。
3. **能力和权限分离**：实验包依赖 `environment.mysql` 等能力，插件自己声明所需读写执行权限，避免把插件类型写死。
4. **失败状态可解释**：缺失、停用、不兼容、冲突和循环依赖都有独立状态，实验包可以只读而不是整个软件不可用。
5. **持久化足够朴素**：两层数据库、JSON、Markdown 和 `experiment_history/` 都便于用户复制和排错。
6. **路线图已有降级路径**：先“能读”，再“能跑”，再“能判”，最后补充生态，不会被第三方扩展阻塞。
7. **Workbench UI 作为独立层推进**：功能栏、主侧边栏、标签页、中央工作区、底部面板和状态栏可以先用静态数据实现，不会阻塞核心解析器和后续数据库。

### 仍然需要严格执行的原则

- `AppContext` 必须是只读能力入口，不能实现成到处可写的模块级单例；
- `WorkspaceContext` 默认不能传给普通插件，跨包能力只能通过一个个明确的核心 API 增加；
- 全局激活和全局权限必须是两个独立概念；
- 插件宿主是进程隔离和崩溃恢复边界，不要在文档或 UI 中称为 OS 沙箱；
- 插件 manifest 的 `provides` 和 `permissions` 不得混为同一个字段；
- 依赖解析必须先于宿主启动，不能启动插件后再临时决定它能访问什么；
- 运行时文件句柄、环境变量和执行计划必须在切换实验包时失效并重新授权。

## 主要风险

| 等级 | 风险 | 影响 | 建议控制 |
|:---:|:---|:---|:---|
| P0 | 插件启动外部程序后绕过逻辑作用域 | 恶意或有缺陷的原生程序可能读取其他文件 | 默认不授予外部执行；开发者模式强提示；所有执行经过 `ExecutionSupervisor`；明确“不提供 OS 沙箱” |
| P0 | 插件依赖解析错误导致错误插件被加载 | 可能运行错误环境、误注册 UI 或使用不兼容 API | 先实现纯函数解析器；覆盖传递依赖、循环、冲突和缺失测试 |
| P0 | 包声明运行依赖但共享依赖状态不可靠 | 实验在一台机器上可用，换包或重启后失败 | 依赖指纹、状态摘要、预检和可复现错误；安装结果不写死在 package.db |
| P1 | 全局插件和包级插件生命周期互相污染 | 切换包后读取上个包文件或保留旧权限 | 每次切换创建新的 `PackageContext`，撤销注册项和文件句柄 |
| P1 | UI 继续停留在临时 Demo 级别 | 用户无法建立稳定的工作区认知，插件、搜索和实验面板后续难以统一接入 | 先完成 VSCode Workbench 外壳和视觉变量，再把阅读器嵌入中央工作区；不把业务逻辑写进布局组件 |
| P1 | 版本范围冲突 | 用户安装多个领域包后某包不可运行 | MVP 只允许一个 ID 一个活动版本；显示冲突链；暂不实现多版本并行 |
| P1 | 内容更新导致进度误重置 | 用户升级后感觉学习记录丢失 | 章节内容指纹；只重置被修改章节；新增未修改章节不影响旧记录 |
| P1 | 进度与实验历史的事实来源混乱 | 数据库变大或无法复制排错 | package.db 只保存摘要，详细输入/输出/错误/产物继续写文件 |
| P2 | 自定义源提供低质量或恶意包 | 用户误信来源 | 导入前显示作者、目标、前置知识、环境、日志、许可证和风险；不把 star 当安全证明 |
| P2 | 全文搜索范围过大导致性能问题 | 学习区包很多时打开卡顿 | 后台建索引、可重建缓存、先支持 Markdown 正文，限制在当前学习区 |
| P2 | 文档先于真实插件协议漂移 | SDK 和示例插件无法兼容 | 先用官方 MySQL 插件验证，契约测试通过后再开放第三方插件 |

## 当前不应提前做的功能

以下内容不属于当前开工阻塞项：

- 中心化包市场、复杂评分、作者审核和企业级证书体系；
- 云账号、远程数据库、同步冲突合并和自动快照；
- OS 级沙箱、容器、完整第三方插件安全审计；
- 同一插件多版本并行加载；
- 自动迁移跨路径进度；
- 平台模拟器和跨平台完美兼容承诺；
- 无障碍完整认证；
- GUI LabKit；
- 教学质量自动评分；
- 自动更新/OTA。

## 未来值得添加的功能

按优先级排序：

### P1：核心稳定后添加

1. 插件缺失/权限请求/依赖预检的统一 UI；
2. 插件崩溃后的停用、重启和最近日志查看；
3. 学习区依赖清理、重建和磁盘占用展示；
4. 包升级时的章节变更预览；
5. 实验历史查看、复制和导出；
6. 用户自定义少量快捷键和插件命令；
7. `labkit validate/preview/pack/inspect-permissions` CLI；
8. 运行报告和崩溃报告的稳定脱敏规则。

### P2：生态形成后添加

1. GitHub/自定义源的轻量下载器和失败重试；
2. 插件安装、启用、全局/包级激活管理页面；
3. 插件 SDK、示例插件和版本兼容检查工具；
4. 用户自定义同步/导入导出插件；
5. 包作者信息、star、日志、许可证和环境说明展示；
6. AI 插件、主题插件、更多领域环境适配器；
7. 笔记、实验标题和资源的可选全文索引。

## 最小开工范围

第一批实现应只包含以下可独立验收的部分：

1. `core-types`：manifest、版本范围、权限、上下文和解析状态类型；
2. `plugin-resolver`：全局插件、当前包直接依赖、递归依赖、缺失/冲突/循环；
3. `dependency-manager`：依赖指纹和学习区 `dependencies/` 路径计算；
4. `package-loader`：包导入、路径安全、manifest 和章节读取；
5. VSCode Workbench UI 外壳：功能栏、主侧边栏、标签页、中央阅读区、底部面板和状态栏；
6. 只读阅读器和当前学习区全文搜索；
6. 最小 `AppContext`/`PackageContext` 和缺失插件提示；
7. 之后才接官方 MySQL 宿主、执行监督、判定和数据库持久化。

验收标准不是“架构文件齐全”，而是：一个本地实验包能被打开，当前学习区能搜索，插件解析结果可解释，缺少插件时可以继续阅读而不会静默执行。

## 最终判断

**设计方向可行。安全和执行风险主要集中在插件宿主、依赖解析和外部进程监督；产品体验风险则集中在 UI 不能停留在临时阅读器级别。** 当前最重要的工程动作是先完成 Workbench UI 外壳，同时继续保持插件 manifest、上下文、权限和解析结果为可测试的纯 TypeScript 类型与函数；真实插件和执行环境仍然后置。
